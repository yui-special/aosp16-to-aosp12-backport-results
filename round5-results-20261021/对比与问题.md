# 7 个 CVE 回移植结果对比与当前问题

生成时间：2026-10-21

## 1. 结论摘要

本轮将依赖 hunk 先分组、再交给回移植模型处理，确实解决了上一版的一批“关键 hunk 根本没进入输出”的问题，但还没有做到可以只凭结果目录宣布 7 个 CVE 全部移植正确。

当前判断：

- **明确改善 3 个**：CVE-2025-48649、CVE-2025-32348、CVE-2025-48595。
- **没有明显提升 2 个**：CVE-2026-0045、CVE-2025-48533。
- **质量回退 1 个**：CVE-2025-48550。
- **必须重新设计 1 个**：CVE-2026-46054。
- 7 个结果中，**没有 1 个可以仅凭当前证据认定为与 AOSP 16 原补丁完全语义等价**。其中最接近可用的是 48649、32348、48595，但仍分别存在调用点、测试闭环或补丁最小化问题。

统计口径：

- 基线：仓库中各 `CVE-*-gpt5.5/2-PortGPT-generated.patch`。
- 本轮：本目录各 `CVE-*/complete.patch`。
- `文件数` 按 `diff --git` 统计，`hunk 数` 按 `@@` 统计。
- 字节数、文件数和 hunk 数只表示 patch 覆盖范围，**不表示语义正确性**。

人工版对比后的总体判断：

- **48649**：已超过旧基线，但仍没有达到人工最终版。

- **48595**：只是安全性覆盖范围比旧基线大，按人工最小版的语义核对仍不合格。

## 3. 三个明确改善的 case

### 3.1 CVE-2025-48649：关键权限 hunk 已补回

基线 patch 缺少权限重置链路中的核心文件，`complete.patch` 中 `GRANTED_BY_DEFAULT` 出现 0 次，说明关键安全语义根本没有进入旧版输出。本轮：

- 文件数从 7 增加到 10。
- hunk 数从 10 增加到 19。
- `GRANTED_BY_DEFAULT` 在当前 patch 中出现 2 次。
- 已覆盖 `LegacyPermissionManagerService`、`PermissionManagerService`、`PermissionManagerServiceInternal` 等上一版缺失的层级。

这证明“把有依赖关系的 hunk 放进同一组”确实修复了“核心 hunk 被遗漏”的问题。

但当前仍有两个实质问题：

1. **比人工最终版少一个 hunk，存在旧调用点未更新。** 人工 `merge-by-hand-3.patch` 是 10 文件 / 20 hunk，当前版是 10 文件 / 19 hunk；缺少的正是 `PackageManagerService` 中 `resetRuntimePermissions(pkg, userId, true)` 的调用调整。应用后代码 `PackageManagerService.java:23005` 仍然是 `resetRuntimePermissions(pkg, userId)`，与三参方法不一致。人工合并结果在这里传入 `true`，从而保持重置用户时恢复预授权权限的原行为。
2. **新分支条件不是 A16 的语义。** 当前 `PermissionManagerService.java` 写成：

   ```java
   if (restorePregrantedPermissions
           && ((oldFlags & FLAG_PERMISSION_GRANTED_BY_DEFAULT) != 0
                   || (oldFlags & FLAG_PERMISSION_GRANTED_BY_ROLE) != 0)) {
   ```

   这会把 `restorePregrantedPermissions == false` 的 default/role 权限推进后面的 `else if`，进而执行 revoke。A16 的逻辑是先识别 default/role 权限，再在内部根据 restore 参数决定是否恢复；参数为 false 时应保持原状态，而不是转换成撤销。

   人工 `merge-by-hand-3.patch` 保留的条件结构是：

   ```java
   if ((oldFlags & FLAG_PERMISSION_GRANTED_BY_DEFAULT) != 0
           || (oldFlags & FLAG_PERMISSION_GRANTED_BY_ROLE) != 0) {
       if (restorePregrants) {
           grantRuntimePermissionInternal(...);
       }
   } else if (...) {
       revokeRuntimePermissionInternal(...);
   }
   ```

   也就是说，当前版在文件覆盖上接近人工版，但在这一个分支上发生了语义收窄。

因此 48649 的判定是 **PARTIAL**：覆盖面有重大改善，但不能直接作为最终补丁。

### 3.2 CVE-2025-32348：进程级 pinned-window 路径已补回

基线只修了 UID 级可见窗口判断，缺少旧版后面的进程级放行路径。当前 patch 中：

- `hasVisibleNotPinnedActivity` 出现 9 次。
- 基线中为 0 的 `hasActivityInVisibleTask` 出现 6 次。
- 基线中为 0 的 `areBackgroundActivityStartsAllowed` 出现 2 次。
- 文件从 3 个增加到 6 个，新增 `BackgroundLaunchProcessController` 和 `WindowProcessController`。

这与人工分析中指出的漏洞绕行链一致：只拦住 UID-level 检查时，旧代码仍可能通过 visible foreground task 的 process-level exemption 放行 PiP。

问题仍然存在：

- 人工 `32348_manual_v2.patch` 只改 4 个核心 Java 文件、9 个 hunk；当前版改 6 个文件、15 个 hunk，额外加入了 `WindowProcessController` 的 visible-not-pinned 状态标志/helper 和两个 wmtest 文件。方向可能合理，但已经偏离人工最小实现，尚未证明等价。
- 额外修改了两个 wmtest 文件，但没有完成真实 wmtest 执行闭环。
- `run.log` 中多次出现“源码可编译，但测试未通过”，最后才报告 backport 成功；不能把最后一行 `Successfully backport` 当成语义验证通过。
- 仍未形成“测试失败 -> patch 修订 -> 再测试通过”的可复核证据链。

判定：**PARTIAL，结构上有明显改善，功能正确性未验证完成。**

### 3.3 CVE-2025-48595：实际编译副本已被修改

gpt-5.5 基线只有 651 B、1 个 hunk，并且主要修改 `dist/sqlite-autoconf-3440300/orig/sqlite3.c`。该 `orig` 副本不参与 Android 实际 SQLite 编译，因此“补丁存在”不等于“编译生效”。

本轮：

- 同时修改 `dist/sqlite-autoconf-3440300/sqlite3.c` 和 `orig/sqlite3.c`。
- `mxTerm` 出现 12 次。
- `SMXV` 出现 5 次。
- `analyzeAggregate` 出现 5 次。
- `iAgg` 出现 4 次。
- `run.log` 记录了编译成功，之后还通过了最小驱动测试。

问题：

- 人工最小版 `48595_manual_2.patch` 是 1 个文件 / 7 个 hunk；当前版是 2 个文件 / 13 个 hunk。当前版更大，但并不是人工版超集。
- 当前版漏掉了人工版的 `#define SMXV(n)`。
- 当前版漏掉了 `AggInfo.nSortingColumn` 从 `int` 改成 `u32`。
- 当前版在列处理路径中漏掉了 `if (k > mxTerm)` 上限检查以及 `assert(k <= 0x7fff)`。
- 当前 `orig/sqlite3.c` 和实际 `sqlite3.c` 都含新代码，但其中仍使用 `SMXV(i16)`，却没有在新文件中定义 `SMXV`。因此日志里的编译通过不能证明最终 `complete.patch` 在干净树上可编译。
- 当前 patch 还包含 `sqlite3BtreeInsert`、`setupLookaside` 等不属于该 aggregate-term 安全语义的改动，存在把 A16 SQLite 3.44.5 升级内容误带入的风险。
- 没有运行真实 SQLite 测试套件。

判定：**覆盖率高于旧基线，但与人工最小版不等价；必须以人工版 `48595_manual_2.patch` 为基础重新收敛，并在干净树上重编译。**

## 4. 无明显提升或质量回退的 case

### 4.1 CVE-2025-48550：当前结果比基线更差

当前 `complete.patch` 引入了：

```java
FrameworkParsingPackageUtils.validateName(...)
```

但 A12 实际对应类是 `ParsingPackageUtils`；`FrameworkParsingPackageUtils` 在 A12 中没有可解析的正式定义。应用后的 `SlicePermissionManager.java` 也没有加入：

- `import android.content.pm.parsing.ParsingPackageUtils;`
- `import android.text.TextUtils;`

`run.log` 中曾经出现过一个带正确 import、使用 `ParsingPackageUtils` 的候选补丁并报告编译成功，但最终 `complete.patch` 没有保留那版实现。这暴露出一个严重问题：**流水线验证的候选与实际交付的 final patch 不一致**。

当前静态检查只检查“新增 import”，因此漏掉了“当前 patch 使用了不存在的类且没有新增 import”的情况，产生了假阳性。

判定：**REGRESSION，不可直接使用。**

### 4.2 CVE-2026-46054：不是继续修 patch 就能解决

当前 patch 添加了部分 SELinux backing-file hook，但 A12 5.10 内核缺少整套前置设施。当前编译失败的关键错误包括：

```text
implicit declaration of function 'backing_file_security'
'struct lsm_blob_sizes' has no member named 'lbs_backing_file'
too few arguments to function 'file_map_prot_check'
```

`complete.patch` 中虽然出现了 `backing_file_security`、`lbs_backing_file`、`backing_file_alloc` 等名称，但它们只是引用不存在的接口，不代表设施已经移植。

更根本的是，A12 目标内核的 overlayfs 路径没有 A16 同等的 backing-file 漏洞前提。当前最多只能得出“该补丁依赖的实现路径不一致”；不能既说目标不存在漏洞，又不给出对应安全论证。

判定：**FAIL / NEEDS_REDESIGN**。下一步应先做目标内核的事实核验和安全影响分析，再决定是不适用、需要等价设计，还是需要一并移植整套设施。

### 4.3 CVE-2026-0045：小步正确，但验证有限

AOSP 16 原补丁中的 aconfig 和 L2CAP 清理内容不适用于当前 A12 结构，真正相关的核心是 `btm_sec_is_upgrade_possible()` 中对临时 bonding 和认证要求的判断。本轮保留为 1 个 hunk，与人工分诊结论基本一致。

当前仅有应用/build 静态验证，没有配对行为测试。判定：**PASS-LIMITED**。

### 4.4 CVE-2025-48533：空补丁是“无落点”，不是“已证明安全”

当前和基线都没有实际代码改动。A12 中缺少 A16 的 aconfig 条件和 `mRemoveAfterTransaction` 对应结构，因此补丁只能变成空补丁。

`run.log` 随后仍报告编译、测试和 PoC 通过，是因为没有可执行内容时这些阶段被当作通过，而不是因为真实修复被验证。A12 的窗口移除逻辑与 A16 不完全相同，必须单独证明该绕过路径在 A12 不存在。

判定：**NOT_APPLICABLE_STATIC_ONLY**。

## 5. 横向问题分类

### P0：最终产物与验证候选可能不一致

最严重的问题不是某个 hunk 写错，而是“验证过的 patch”和“最终写出的 patch”可能不是同一份。48550 已经出现直接证据：日志中可编译的候选带正确 import 和 `ParsingPackageUtils`，最终交付文件却使用 `FrameworkParsingPackageUtils` 且没有 import。48595 也存在相同风险：最终 patch 引用 `SMXV`，但交付文件中没有定义，日志中的编译成功不能证明最终文件在干净树上可编译。

要求：

- final patch 必须是最终通过验证的同一个字节序列。
- 验证前从干净目标树重新 `git apply`，禁止复用上一次残留的工作区状态。
- 记录 final patch SHA-256，并把它写入状态文件。

### P1：hunk 覆盖不等于完整语义

分组能改善“相关 hunk 被拆散”的问题，但不能自动回答：

- 哪个新符号需要同时新增；
- 哪个旧调用点必须一起改；
- 哪个 `else` 分支在旧版有不同含义；
- 哪个 helper 或基础设施在 A12 根本不存在。

48649 的三参调用遗漏、48550 的 import/类名错误都属于这一类。

### P1：缺少“语义等价”检查

当前检查主要证明：

- patch 能应用；
- 某些符号存在；
- build.sh 的有限检查能通过。

它不能证明安全义务等价。至少需要按 CVE 建立 obligation 表，例如 48649 必须同时覆盖：

1. 三参 API 与所有调用点；
2. restore=true 时恢复预授权；
3. restore=false 时保持原状态；
4. 权限层和 AMS/PM 的跨层调用一致。

### P1：空操作和缺少测试文件会被误报为 PASS

48533 的空补丁、部分 case 缺少 test.sh/poc.sh，以及“没有文件改变所以编译通过”，都会造成虚假的绿色状态。应当区分：

- `PASS`：真实执行并通过；
- `SKIPPED`：缺少测试入口；
- `NO_OP`：没有代码变化；
- `NOT_APPLICABLE`：有明确代码事实证明不适用。

这四种状态不能共用同一个 `PASS`。

### P2：patch 最小化和上游噪声

48595 当前包含与 aggregate-term 安全修复无关的 Btree/lookaside 改动。A16 提交本身可能包含版本升级噪声，回移植应只保留目标漏洞所需语义，不应整包照搬。

### P2：模型输出存在采样波动

本轮移植模型为 `gpt-5.5`、temperature 1.0；分组和摘要使用 `DeepSeek-V4-Pro`、temperature 0。相同流程下 48649 两次结果接近，但 48550 一次能生成正确类名，另一次生成不存在的类，说明最终结论不能依赖单次采样。

建议：

- 移植模型温度降到 0 或接近 0；
- 每个高风险 case 至少重复两次；
- 选择标准是“编译 + obligation 表 + 差分检查”，不是“某次日志写 Successfully”。

### P2：网关稳定性

本轮流程曾在 GreatRouter 兼容端点上遇到 TLS 握手卡住、urllib 半关闭挂起、较大请求 ReadTimeout/WriteTimeout，以及并发升高后端点不可用。当前已通过强制 TLS 1.2、显式超时和串行执行规避大部分问题。

网关故障会影响可复现性，但 46054 的最终失败原因是内核源码编译错误，不是网络中断。

| 2025-32348 | patch 覆盖 UID 级和进程级路径 | 真实 wmtest 通过、无重复或越界修改 |

| 2025-48550 | patch 能应用；存在相关语义尝试 | 干净树上可编译、import/类名正确 |

## 7. 下一步优先级

1. **先修 48550 的 final patch/验证候选不一致问题。** 这是整个流水线的可信度问题，不只是一个 CVE 的代码问题。
2. **修 48649 的旧调用点和 restore 分支。** 与人工 `merge-by-hand-3.patch` 对齐后再做干净树编译。
3. **以 `48595_manual_2.patch` 为基准重做 48595。** 补回 `SMXV`、`nSortingColumn` 和列索引上限检查，删除 Btree、lookaside 等无关噪声，再在干净树重编译。
4. **32348 执行真实 wmtest。** 只有真实测试通过后才从 PARTIAL 升级。
5. **46054 进入重新设计流程。** 先证明 A12 漏洞前提和受影响调用路径，再决定实现方案。
6. **48533 和 0045 补“不适用/行为有效”的证据。** 静态存在性检查不能作为最终安全证明。
7. 在流水线层面增加：
   - final patch 哈希与干净树重放；
   - obligation 表逐项检查；
   - `PASS/SKIPPED/NO_OP/NOT_APPLICABLE` 四态；
   - 空补丁自动拒绝；
   - 高温度重复采样和一致性选择。
